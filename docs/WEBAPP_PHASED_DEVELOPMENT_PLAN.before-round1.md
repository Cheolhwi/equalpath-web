# EqualPath 新版网页分段开发计划

日期：2026-09-12。状态：阶段 0 的首批数据采集与 Appwrite 入库已执行；网页接口接入、行政边界复核及各 Epic 功能验收仍未完成。

最新范围补充：用户已授权采集新版所需数据，并存入现有 Appwrite 服务。当前服务范围限定为吉隆坡联邦直辖区与雪兰莪州。已读取 1,216 条既有区域 JKM 记录，并采集 2,323 条区域幼儿园公开目录记录、117 条 MBPJ 历史名单，写入独立 `web_` 资源。KPM 学校代码保留第三方来源，尚未完成官方核验；当前地区筛选依据来源地区字段，行政边界与疑似跨分支匹配仍需复核。具体数据、Epic 对应关系和读回证据见 [数据执行记录](webapp-data/EPIC_DATA_MAPPING.md)。

## 方向与范围

这是全新设计的无登录 Web App。iOS 暂时搁置，其历史 Epic、用户账户、日程、协调和求解器不作为新版软件的功能基线。

继续使用现有 Appwrite 基础设施，包括已有项目配置及域名资源。新版网页建立自己的业务数据、接口契约和资源命名空间；原资源是否被引用、需要新增哪些资源，在阶段 0 形成明确清单。不会为了重建网页而清空旧数据或整体推送旧后端配置。

需求以 `design artifacts/EqualPath_WebApp_Epics_User_Stories_DOD.docx` 为准：8 个 Epic、48 个 User Story、96 条 AC。配套 Data Management Plan 和 Security Plan 提供数据与发布要求。文档中的 Planned 和未来 DOD 不代表已有交付。

现有 `design-prototypes/rhine-map/` 作为视觉和交互参考：保留平面 OpenStreetMap、莱茵式排版、细线和克制配色，不加音乐。现有示例筛选、收藏和比较只算原型，不直接计入新版验收。

新版主要任务：填写一次临时照护需求 → 找机构 → 分项检查条件 → 比较证据 → 准备问题并自行联系。收藏、准备、分享和演练也允许独立进入，不设置强制向导。

## 地区范围

- 只服务 **Kuala Lumpur 和 Selangor**，以经核实的行政归属为准。不会把模糊的“大吉隆坡”“巴生谷”宣传标签当作地区边界，也不会把名称或邮寄地址里出现 KL 的机构自动归入吉隆坡。
- Putrajaya 及其他州属不纳入本版服务范围。吉隆坡与雪兰莪之间可跨界搜索；扩大半径仍受这两个地区约束。
- 采集任务限定目标地区，新版正式目录入库再次检查归属，公开搜索与详情接口再次执行地区限制；不能只靠前端隐藏其他地区。
- 接送地点选择也限定服务区。用户输入区外地点时明确提示服务范围，保留其他有效输入，不返回伪装成本地结果的机构。
- 地址、坐标或来源所属地区互相矛盾的记录先留在受限的待核对区，不猜测后直接发布。已能确认行政归属但缺坐标的机构仍可进入列表，地图不制造标记。
- 行政边界和地区别名保存来源与版本；跨品牌、跨州的连锁机构按具体分支处理。既有 iOS 或历史数据库中的其他地区记录不因本次范围缩小而删除。

## Appwrite 与前端的职责

| 内容 | 拟定位置与边界 |
|---|---|
| 页面、表单、地图与交互 | 新网页前端；沿用原型视觉，按新版业务组织组件与状态 |
| 项目、部署与域名 | 沿用 Appwrite 基础设施；先核对现有域名绑定、环境和回退方式，生产切换另列发布任务 |
| 已审核的机构目录、分支身份和来源证据 | Appwrite 数据库；服务字段、注册记录、费用单位、来源日期、抓取日期和版本分别保存 |
| 公开搜索、详情与条件检查 | Appwrite Functions；只返回网页允许展示的字段，不接入旧 iOS owner 数据或日程 |
| 收藏、非识别性备注和需求模板 | 当前浏览器；不自动创建家长账号或同步到云端 |
| 单次未保存的需求 | 页面状态及必要的临时处理；不建立用户搜索历史 |
| 分享卡、卡片版本与演练快照 | 用户明确创建后存入 Appwrite；读链接与编辑链接分别校验权限 |
| 地图与路线 | OSM 数据/瓦片服务提供平面地图；路线估算是独立依赖，可由 Function 获取。地图本身不提供真实行程时间 |
| 来源采集、导入与发布 | 由开发任务完成 KL/Selangor 定向采集、清洗和 Appwrite 入库；采集可在适合的执行环境运行，来源与导入记录保存在 Appwrite，不强制把长时间采集塞进网页请求 |

资源命名建议使用一致的网页专属前缀，例如 `web_`，最终名在阶段 0 锁定。机构事实、来源记录、注册证据、评论、私密卡片是不同数据组，具体表的合并或拆分按查询和权限需要决定，不提前堆砌表。

Appwrite 支持公开执行的 Function，但公开入口不等于开放数据库写入。服务端 API key 可以越过行权限，因此分享卡必须在 Function 内逐次检查凭据、目标卡片和操作权限；密钥不进入前端。[Function 执行文档](https://appwrite.io/docs/products/functions/execute)、[权限文档](https://appwrite.io/docs/advanced/security/permissions)。

## 开发顺序

首轮交付为阶段 0–3，形成能完成联系决策的网页。阶段 0 同时建立网页基础与地区数据流程，先用 Demo 校验契约，再把完成来源核对的第一批真实目录接入阶段 1；不把示例数据交付当作真实数据完成。然后完成阶段 4–5。阶段 6 的评论采集由开发负责，可随机构分支匹配逐步开展，不阻塞阶段 7；阶段 8 必须在阶段 2 和 7 稳定之后开始。

## 数据采集与入库工作包

| 批次 | 需要取得的数据 | 拟采用的来源 | 支持的功能 |
|---|---|---|---|
| D1 地区与机构底册 | KL/Selangor 边界、地区别名、机构分支名称、类别、公开地址、坐标、注册证据 | OSM、现有地区映射、JKM TASKA/相关 Pusat Jagaan、KPM 对应机构记录 | 阶段 1 搜索地图、阶段 3 证据 |
| D2 服务与联系资料 | 公共电话、年龄段、临时接收政策、照护时段、接送类型及覆盖、收费单位和规则 | 机构官网/公开资料、Kiddy123 等目录及相关机构来源 | 阶段 2 条件检查、阶段 3 比较联系 |
| D3 评论证据 | 正确分支的评论、原始日期、获取时间、来源链接、样本范围、主题与可用摘录 | 具体第三方公开评论来源，例如 Google Maps 可用来源或授权导出 | 阶段 6 评论与询问清单 |

以上是采集目标与候选来源，不是完整字段可获得的承诺。执行时先验证来源访问与可用内容；某个来源无法取得时记录缺口并继续其他来源。没有公开说明的临时接收、接送范围、时间例外或费用保持未知，不能通过爬取推断实时空位。

采集流程：**地区筛选 → 记录原始来源 → 分支匹配与去重 → 字段标准化 → 校验 → 写入新版 Appwrite 目录 → 读回核对 → 网页联调**。

- 每条发布事实关联具体分支、来源引用、原始口径、来源日期（如有）、获取日期及版本；注册记录、机构自述和评论分开。
- 同品牌的不同分支不会因为名称相似而合并。电话、地址、来源 ID 和坐标作为身份核对信号；有矛盾时保留冲突。
- 导入可断点续跑；重复运行更新相同来源记录，不重复堆积机构。失败批次不切换当前可用目录，不把缺页当作源机构已删除。
- 正式发布前记录两地区各自的来源覆盖、记录数、分页完整性、缺字段数、无法匹配数和日期；总数只来自实际采集与读回，不预先承诺覆盖率。
- Appwrite 写入仅针对新版已确定的资源。API key 由服务端/受控采集环境使用；浏览器只访问允许公开的接口。原始采集工作材料与公开字段分开存放。
- 第一轮需要实际验证重复导入、失败重跑、来源更新失败、区外记录拒绝和前后端结果一致。更新频率在首批采集耗时、来源情况与 Appwrite 配额核实后确定，不提前宣称定时任务已运行。

## 阶段 0 新网页基础

1. **P0.1 项目与资源清单**：核对现有 Appwrite 项目、数据库、Functions、网页部署和域名绑定；列出新增、复用和不涉及的资源。不用旧 iOS 配置整体覆盖云端。
2. **P0.2 新前端骨架**：整理导航、页面路由、设计变量、通用弹层和状态；把原型里的数据、查询逻辑、条件检查与页面展示分开。粗版继续保留供对照。
3. **P0.3 数据与接口契约**：定义机构分支、来源记录、逐字段证据、费用单位、时间适用范围、坐标、分支匹配状态和事实版本。定义查询输入、分页、错误与响应格式。
4. **P0.4 受控样例连接**：准备明确标为 Demo 的吉隆坡与雪兰莪数据，覆盖已知、未知、冲突、同品牌不同分支、缺坐标、过时来源和区外拒绝等情况；接通新版接口及独立测试资源。
5. **P0.5 验收台账**：建立 96 个精确 AC ID 对应的状态和证据位置，区分未做、局部完成、集成待验、已验证及评审结果。
6. **P0.6 定向采集**：实现 D1 的 KL/Selangor 来源筛选、分页、重试和来源登记；检查 D2 的可获取字段，按分支补充公开联系方式与服务资料。
7. **P0.7 清洗与地区校验**：完成分支去重、来源匹配、费用和时间口径、坐标及行政归属检查；歧义记录与正式目录分开。
8. **P0.8 Appwrite 入库与读回**：在新版资源中执行可重复导入，校验写入前后的记录与关键字段；让阶段 1 使用首批已审核真实数据，并保留 Demo 用于可重复测试。

完成标志：网页能从指定 Appwrite 接口读取首批 KL/Selangor 目录及来源，已知采集缺口可查；页面不含密钥；新版请求不依赖 iOS 账号或日程；数据结构可支持后续条件解释和来源变更。基础框架可先预览，数据任务未完成时仍单独标为未完成。生产域名切换另列发布任务。

## 阶段 1 搜索与平面地图

1. **P1.1 一次性需求表单（1.1–1.3）**：公共接送地点、日期、最迟接走时间、照护结束时间、年龄段、机构接送或自行送达。实现缺项和时间顺序校验，保留有效输入。
2. **P1.2 搜索和列表地图联动（1.4）**：地图保持平面；列表和标记引用相同候选集合。缺坐标机构继续留在列表，地图故障时仍可浏览。
3. **P1.3 修改与失败恢复（1.5–1.6）**：修改时间或地点后重新查询；旧结果标明对应旧需求；区分没有匹配项与服务暂不可用，提供重试和主动放宽条件。
4. **P1.4 服务地区约束**：地点、搜索、详情和推荐统一限制 KL/Selangor；半径放宽不能越过服务区。验证边界附近、同名地点、直接请求区外机构 ID 与返回访客的旧区外地点。

原型调整：将目前的月费筛选和普通机构推荐重点，改为本次接送与临时照护需求。保留可用的机构卡、地图选中和详情交互。

完成标志：新访客无需登录即可完成搜索；清楚看到候选、解释过的空结果或可恢复错误。逐条验证 1.1.1–1.6.2。

## 阶段 2 单个机构条件检查

1. **P2.1 年龄与临时接收（2.1）**：分别检查招生年龄和一次性接收政策；普通 daycare 或月度项目不推断为接收临时照护。
2. **P2.2 接送与时间（2.2–2.4）**：分别检查机构自营/合作接送、覆盖范围、接走窗口、路线证据、适用日期的照护时间和延时规则。一般营业时间与临时照护时间独立。
3. **P2.3 排序与解释（2.5–2.6）**：使用用户选择的距离、最晚结束时间或公开接送因素排序；缺值明确列出。每个条件输出符合、冲突或未知、原因、来源及可转入的问题。

后端任务：建立可独立验证的条件规则模块，供当前搜索和后续演练共用；结果附需求版本与事实版本。路线服务缺失时返回未知，不用直线距离换算时间。机构接送线路不明确时，普通道路路线估算不能当作真实接送路线。

完成标志：用户能解释某候选的适用条件和待确认事项；未知不会变成完整安排通过。逐条验证 2.1.1–2.6.2，前往询问清单的实际集成在阶段 3 验证。

## 阶段 3 证据、比较与联系

1. **P3.1 注册证据（3.1–3.2）**：展示分支对应的 JKM/KPM 记录、来源与已公开字段；区分匹配、匹配待确认、记录到期和身份不一致。未取得记录不表示机构未注册。
2. **P3.2 比较与费用（3.3–3.4）**：多机构使用一致字段；区分临时入托、交通、时间、地点、注册和未知项。仅在适用费率和全部必要费用规则齐备时计算参考合计；月费保留月费口径。
3. **P3.3 问题和自主联系（3.5–3.6）**：根据当前需求与未知项生成、去重并复制问题；用户主动使用电话或来源链接；返回时保留比较候选，不记录联系成功或接收结果。

后端任务：发布可追溯的注册、服务与收费证据，完成详情/比较响应；问题生成使用可解释规则，不增加聊天机器人前置依赖。

完成标志：完成“需求 → 候选 → 条件 → 比较 → 联系问题”的真实浏览器流程。这是首个完整功能版本。评论关切的真实集成条件 3.5.2 在阶段 6 补验，台账保留该依赖。

## 阶段 4 收藏与需求复用

1. **P4.1 本地保存（4.1–4.3）**：收藏分支、非识别性备注、常用公共接送地点、结束时间与接送偏好；每次新请求重新选择日期。
2. **P4.2 复用与管理（4.4–4.5）**：从收藏/模板发起新搜索，编辑删除本地内容；不改变机构原始事实。
3. **P4.3 保存失败与资料变化（4.6，4.1.2）**：存储满或不可用时给出明确失败反馈；公共地点失配要求重新选择；事实版本变化时提示重查，不沿用旧匹配结果。

完成标志：返回访客能复用信息，但得到针对新日期的新检查；无自动云同步。4.5.2 与分享卡的独立管理关系在阶段 7 补验。

## 阶段 5 准备与交接清单

1. **P5.1 本次安排清单（5.1–5.2）**：按机构接送/自行送达、照护时长和事实生成清单；问题分给原机构、接收机构和运输服务方。
2. **P5.2 顺序和手续（5.3–5.4）**：展示接走、转送、最终接回的顺序；明确请求假设、来源事实、估算与未知；提供离园、身份核验和迟到处理问题。
3. **P5.3 离线准备与打印（5.5–5.6）**：输出物品和线下信息提示、打印样式；不在线收集儿童身份、证件或健康信息。打印文档不表示接送授权或机构同意。

完成标志：首次和重复使用都能生成针对本次需求的清单，并得到可读打印件。向分享卡附加允许内容的 5.6.2 在阶段 7 补验。

## 阶段 6 家长评论证据

1. **P6.1 语料接入（6.1，6.5）**：接入有明确来源、分支匹配、采集范围和可用条件的评论；与目录宣传、编辑介绍分开。原始发表时间、日期精度和获取时间独立。
2. **P6.2 主题与原文（6.2–6.3）**：按接送、临时入托、晚接、费用和沟通筛选；摘录保持上下文；没有某主题证据就显示不足。
3. **P6.3 样本与提问（6.4，6.6）**：显示已收集数量、近十二个月范围和日期未知数量；至少两条独立评论才生成重复关切建议；转成中性问题并接入阶段 3。

数据依赖：由开发完成 D3 的采集与导入，不要求用户自行准备评论数据。本段可用明确标注的样例先开发交互，真实评论交付以实际取得的可追溯语料为准；只采集已经匹配到 KL/Selangor 分支的评论。可后移，不阻塞首轮和无登录分享卡。

完成标志：每条摘录和重复关切可追到具体来源；抽样不冒充全平台覆盖；同时补验 3.5.2。

## 阶段 7 无登录分享卡

1. **P7.1 联系卡编辑（7.1–7.2）**：选择、排序第一联系和备选机构；显示公共电话、地点、时间限制和关键问题，只上传用户允许的最小上下文。
2. **P7.2 读写权限（7.3–7.4）**：生成不同的不可预测读/编辑凭据；服务端只存用于校验的凭据摘要；每次按卡片和操作检查。只读输出不包含编辑凭据；丢失编辑链接不承诺无身份找回。
3. **P7.3 打印与来源变化（7.5，7.6.1）**：跨设备手机查看、打印/PDF，包含修订日期和只读在线核对入口；保留顺序并提示机构事实变化。完成 4.5.2、5.6.2 联动。
4. **P7.4 撤销与恢复（7.6.2）**：撤销后拒绝旧在线链接；避免缓存再次暴露内容。落实删除、备份和恢复时的撤销状态，告知离线副本无法召回。

后端任务：新增卡片、修订和权限校验能力；公开访问不直接获得卡片表的列表或写权限。限制创建频率与载荷大小，排除备注、密钥及完整需求进入日志。域名、日志、缓存和导出都检查凭据泄漏。

完成标志：另一台设备无需登录能读取卡片；持读链接无法编辑或撤销，其他卡片凭据也无效；撤销后在线访问被拒绝。删除和备份保留期按配套计划落地并实测，不能只在页面宣称。

## 阶段 8 情景演练

1. **P8.1 场景输入（8.1–8.2）**：晚半小时、晚一小时、首选不可用、接送不可用及自定义一次性变化；缺基准时间要求补充，不生成默认日程。
2. **P8.2 分项重查与共同弱点（8.3–8.4）**：复用阶段 2 规则，逐机构解释变化；识别相同结束时间、都需自行送达等共同限制，区分缺信息和已知弱点。
3. **P8.3 行动与版本（8.5–8.6）**：明确冲突跳转搜索替代项，未知跳转准备问题；主动保存时记录场景、事实版本、状态与检查时间；重查保留旧快照并解释差异。

完成标志：用户能从失败或未知条件走到下一步；不输出成功概率、健康分或已安排照护结论；卡片基线和历史快照不会被未保存演练覆盖。

## 每段交付与验收办法

每段交付一个可打开的网页版本、变更说明、对应 AC 的结果与证据，以及尚未完成的跨段依赖。阶段性界面完成与整个 Epic 满足 DOD 分开记录。

- 用标注 Demo 的已知、冲突和未知样例验证逻辑，同时明确真实数据接入状态。
- 在浏览器中完成本段用户任务，检查手机布局、键盘和焦点、文字放大；涉及打印时打开实际输出检查。
- 按本段相关性检查空数据、地图失败、请求失败、浏览器保存失败和来源过时；失败不默默替换旧结果或刷新来源日期。
- 需要共享的模块检查读写权限、跨卡片拒绝、导出内容、撤销及恢复；运营发布权限与家长访问权限分离。
- 源码构建或单元测试通过不代替用户流程验证；团队/导师评审、治理更新与发布均记录实际发生的结果。
